description: Review the approval queue; record approve/reject; move decided rows to the decision log.
---

Help Meet review pending actions in `Company_OS/APPROVALS_QUEUE.md`.

0. **Pull in managed-agent drafts first.** Several department agents (SEO/AEO, Google Ads, ...) run autonomously on a schedule in the cloud and commit their drafts straight to `origin/main` — a different branch from wherever this session's working copy is (often `slack-integration`). Their rows never reach `APPROVALS_QUEUE.md` on their own, so skipping this step means silently missing whatever they drafted since the last merge.
   - `git fetch origin` (read-only, no push).
   - For every `Company_OS/departments/<dept>/queue-inbox.md`, compare the local file against `git show origin/main:Company_OS/departments/<dept>/queue-inbox.md`. Any row present (or updated — status/escalation changes) on `origin/main` but not locally is an unreviewed managed-agent draft.
   - Update the local `queue-inbox.md` copies from `origin/main` (never drop VOID/closed history), then merge the genuinely new `pending` rows into `APPROVALS_QUEUE.md`, continuing each department's own id sequence — the same manual-merge step `/approvals` already does for same-session drafts, just sourced from `origin/main` too.
   - Tag each merged row with its provenance (e.g. "from origin/main managed-agent run, 2026-08-03") so Meet knows it wasn't drafted in this session.
1. Read `Company_OS/APPROVALS_QUEUE.md` and render every `pending` row (including anything just merged in step 0) in a clear, scannable list grouped by department, each with: id, action, rationale, data-basis, risk, reversibility.
2. For each, present a crisp recommendation (approve / reject / needs-info) with one line of reasoning grounded in `COMPANY_STATE.md`. Do **not** decide for the human — wait for their call. Use the AskUserQuestion flow if helpful to batch decisions.
3. When the human approves or rejects items:
   - Set the row's `status` in `APPROVALS_QUEUE.md` to `approved` or `rejected`.
   - Append a corresponding row to `Company_OS/DECISION_LOG.md` with `decision`, `approved-by` (Meet), `executed = no` for approved items (`n/a` for rejected), and a note.
4. **Propagate every decision into that department's own `tracker.md` + `queue-inbox.md`.** This is not optional bookkeeping — the managed agents never read `APPROVALS_QUEUE.md`/`DECISION_LOG.md` at all (e.g. `google-ads.agent.yaml`: *"NEVER TOUCH `APPROVALS_QUEUE.md`. NOT READ, NOT WRITE."* — there's a whole incident logged there about why). They read only their own `tracker.md` + `queue-inbox.md` + `learning-log.md`. Skip this step and the next scheduled run still sees decided rows as `pending` and may re-draft or re-escalate something Meet already resolved — this is the exact failure class `513da6f` (SEO-013..019) was written to fix.
   - For each row just decided, find it in the department's `queue-inbox.md` and append the decision to its status field **in that file's existing voice** (mirror how already-resolved rows in the same file read — e.g. `✅ **APPROVED by Meet <date> via /approvals — awaiting `/execute-approved`.**`, `❌ **REJECTED by Meet <date> via /approvals.**`, `✅ **EXECUTED (per Meet), <date> via /approvals.**`). Update every place the row appears — several departments (google-ads, at least) keep both a full detail table *and* a short "Live, awaiting action" summary table; both need the update.
   - Add one short dated note near the top of `tracker.md` (wherever that department keeps its running status header/snapshot) summarizing what was decided this cycle, so the agent's very first read already has it — don't rely on the queue-inbox row alone.
   - If a department's IDs collide across branches (this happened with meta-ads: `origin/main`'s own `MA-031..038` vs. a different local batch reusing the same numbers) resolve it the way that department already resolved it — check for an existing renumbering/collision note before assuming which row a decision applies to. Don't invent a new numbering scheme.
   - Departments with no `Company_OS/departments/<dept>/` directory (e.g. ad-hoc CRO work) have nothing to sync — say so, don't fabricate files.
   - **Before writing:** `git fetch origin` again (state may have moved since step 0, including mid-session — managed agents push to `origin/main` on their own schedule, not around you). Build the change on the *current* tip of `origin/main`, not an earlier snapshot or the local branch's copy — the local branch is very likely stale on these specific files (they're actively written by cloud agents). Verify the target rows exist in that fresh copy before editing.
   - **Commit + push these department files straight to `main`** (this step's whole purpose is making the change visible to the next cloud-scheduled agent run — a local-only edit doesn't accomplish that). If the branch you built on is still `origin/main`'s current tip, push directly (fast-forward, no PR needed). If `origin/main` has moved again since you fetched, re-fetch and rebuild rather than force-pushing over it.
5. **Prune each touched department's `queue-inbox.md` — this is the step that keeps the file cheap for the agent to re-read every scheduled run.** The department agents themselves are instructed to never shrink this file (by design — they can't safely tell "decided and safe to compress" apart from "still pending" mid-run). You can, because you just pulled the fresh state from `origin/main` in step 0/4 and know exactly what's resolved. For every row that is now terminal (`approved+executed`, or `rejected`, or closed/informational with no further action):
   - Replace its full original text (rationale, data-basis, the whole decision-annotation trail) with a single compact line: `id | one-line summary | resolution + date`.
   - Move that compact line into a `## Resolved (compact)` section at the bottom of the file.
   - Keep the department's `## Live, awaiting action` (or equivalent) table current and accurate — that table plus any still-`pending` rows is deliberately **all** the department's scheduled agent needs to read each cycle; it should never need to re-derive status by parsing old rows' resolution history.
   - **Never delete anything outright.** The full detail is already permanent in `DECISION_LOG.md` (and `APPROVALS_QUEUE.md` until archived) — this step only compresses the department's own working copy, which exists purely to feed the next scheduled agent run cheaply, not as the historical record.
   - Commit + push this alongside step 4's changes.
6. Approved items now await `/execute-approved`. Remind the human that **nothing is live yet**.

This command edits files only (queue + decision log + department tracker/queue-inboxes). It performs **no** live writes to Shopify/Meta/Gmail/etc. Pulling from `origin/main` in step 0 is read-only (`fetch`/`show`). Step 4's department-file propagation **does** push to `origin/main` — that's the point, so the next managed-agent run sees the decision — but only ever to `tracker.md`/`queue-inbox.md`/`APPROVALS_QUEUE.md`/`DECISION_LOG.md`, never to a live connector.

$ARGUMENTS can filter to a department slug or a specific row id.
